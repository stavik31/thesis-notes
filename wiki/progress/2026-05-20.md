# 2026-05-20 — LLM Fine-tuning Complete, Test Evaluation Run

## What Was Done

Full fine-tuning run of Gemma-3-4B-IT on STATS19 crash narratives completed. Model confirmed as `google/gemma-3-4b-it` (4B, not 7–12B as previously noted — wiki updated). Training used Unsloth + QLoRA on RTX 5080 (16GB VRAM).

**Data setup:**
- Downsampled all three classes to Fatal count (~7,491 each) → ~20,226 training records
- Rationale: avoids 3× dataset inflation from oversampling; Fatal is the hardest class and the minority
- Val set: full 25,174 records (unbalanced, reflects real distribution)
- Test set: full 25,174 records (held out until this session)

**Training config:**
- LoRA r=16, alpha=32, dropout=0.05, all 7 projection layers
- 3 epochs, LR 2e-4 cosine, effective batch 16, bf16
- Eval every 500 steps; best checkpoint saved by eval_loss

**Eval loss curve:**

Loss converged cleanly at epoch 3 with no overfitting — train and eval loss nearly identical throughout. Best adapter: `checkpoint-3500`.

**Test set results (25,174 records, batched generation, batch=16):**

| Class   | F1    |
|---------|-------|
| Slight  | 0.693 |
| Serious | 0.364 |
| Fatal   | 0.134 |
| **Macro** | **0.397** |

**Confusion matrix observations:**
- Slight: 10,926 correct, reasonable performance
- Serious: 2,575 correct but 1,301 predicted as Slight and 1,622 as Fatal — model has no clean boundary for Serious
- Fatal: 311 correct but badly hurt by false positives (2,352 Slight and 1,622 Serious predicted as Fatal)

## Key Decisions / Observations

**Downsampling over oversampling:** Oversampling to majority class count (~1M records) was rejected — it triples training time with diminishing returns. Downsampling to Fatal count (~22.5k) keeps training fast and forces the model to learn all three classes equally. The thesis purpose is domain adaptation, not calibrated classification.

**Classification F1 is a proxy metric:** The model's deployed job is RAG narrative generation, not severity classification. F1 here measures whether domain adaptation worked, not deployment performance. Even modest improvement over zero-shot baseline justifies the fine-tuning for RAG purposes.

**Serious class is the hard problem:** Serious injuries sit between Slight and Fatal with no clean boundary in the narrative features. This is expected — the same ambiguity exists in the tabular baselines. Worth noting in the thesis.

**Gemma3 Processor quirk:** `FastLanguageModel.from_pretrained` returns a `Gemma3Processor`, not a plain tokenizer. Any direct tokenizer operations (padding, encoding) must use `tokenizer.tokenizer` to access the underlying text tokenizer. `tokenizer.tokenizer.pad_token = tokenizer.tokenizer.eos_token` required for batched inference.

## Next Steps

1. **Zero-shot baseline** — run `evaluate.py` with base `google/gemma-3-4b-it` (no adapter) on the same test set. Compare macro F1 to determine whether fine-tuning added value.
2. **XGBoost baseline** — run existing XGBoost model on the same test split for tabular vs. narrative LLM comparison.
3. **Interpret results** — if fine-tuned > zero-shot: domain adaptation worked, proceed to RAG Phase 2. If similar: base model already understands crash language, fine-tuning may be optional for RAG. Either is a valid thesis finding.
