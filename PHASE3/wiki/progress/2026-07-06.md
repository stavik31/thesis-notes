# 2026-07-06 — Engine rebuilt, validated leakage-free, and made explainable

Big session. It closes the 2026-07-04 loose ends, **commits the method decision**, and produces
the implementation blueprint for the Stage 3 rewrite ([[wiki/build/stage-3-cluster-share-engine]]).
All work is real committed scripts in `code/tests/cluster_risk/` (not ad hoc this time), but nothing
is yet folded into the main pipeline — that's the next task.

**Headline:** the 2026-07-04 "validated" result had been run ad hoc and **the code was gone** (never
saved — confirmed via bash history + filesystem). Rebuilt it from the wiki prose, reproduced it,
then went much further: a proper **leakage-free national validation** (spatial CV + an unseen-year
2024 check) confirms **no leakage**, and two explainability layers were added. **Method decision is
now final: XGBoost cluster+share is the engine; GAT is retired to a documented alternative.**

---

## 0. The vanished code (why the session started with a rebuild)

The 2026-07-04 night result (discrete network clusters + share target + separate XGBoost, ρ=0.201
Manchester holdout, 3.10/5 routing divergence) was run inline in a shell and **never written to a
file** — no `.py`, no notebook, no intermediate CSVs (verified). The single best result in the
thesis existed only as deleted scratch. So step 1 was rebuilding it as durable code, which the
2026-07-04 note itself had flagged as "needs a real implementation eventually."

## 1. Reconstruction + validation of the recipe

Rebuilt as `code/tests/cluster_risk/{common,run_xgb}.py`. Reproduces 2026-07-04 faithfully:
- **National in-sample eval = 158,237 crash-bearing segments — exact match** to the recorded number
  (strong evidence the pipeline is faithful). Cross-type ρ ≈ −0.08, Jaccard ≈ 0.002.
- **Genuine single-city spatial holdouts:** Manchester ρ=−0.039, London ρ=−0.096 — far below the
  collapsed GAT (0.855) and best old-GAT (0.377). XGBoost beats the pure statistic on validity for
  most types. (National in-sample is *circular* — trains on target-window cluster aggregates and
  evals on target crashes — so it's decorative; the holdouts are the trustworthy numbers.)

Mechanism (unchanged from 07-04, now re-confirmed): any signal shared across types collapses
divergence; **divergence lives in location, not volume**; the fix pools by network location,
predicts each type's *share*, and shares nothing across types.

## 2. GAT vs XGBoost on the *same* recipe (2026-07-04 open item #1, resolved)

Built `run_gat.py` — 5 fully separate GATs (no shared backbone, no type embedding), same
cluster+share features/target. Verdict:

| | XGBoost | GAT |
|---|---|---|
| Divergence ρ (Manchester / London) | −0.039 / −0.096 | −0.040 / −0.087 (**tie**) |
| Validity vs real crashes | positive everywhere | **negative for car/cycle/lgv** (worse) |
| Held-out-city routing divergence | 1.30 | **2.10** (GAT's one edge — message passing propagates into a novel area) |
| Cost / explainability | seconds, SHAP | minutes/type, opaque |

→ **XGBoost ships.** GAT ties divergence but loses validity + simplicity + explainability; its only
advantage (routing into zero-history regions) isn't a current goal.

## 3. Routing divergence: it needs cluster context (important nuance)

On a **fully held-out** city, routing divergence is weak (mean distinct routes/5: λ=1→1.30,
λ=3→1.50, λ=5→1.60 — λ barely a lever). Mechanistically correct: holding a city out **zeroes its
cluster/location context**, leaving only segment features (own-AADF), which are cross-correlated
across the motor types (car–lgv AADF r=0.977) → they clump onto one route. The **full production
surface restores it** (λ=1→1.90, λ=3→2.20). So:
- **Route on the full-history surface, not a holdout surface** (holdout is validation-only).
- My means (1.9–2.2) sit below 07-04's 3.10 — attributable to O-D pair sampling + λ; the *pattern*
  reproduces (most pairs diverge; some are one-corridor geographic dead-ends, like 07-04's pair 1).

Reference: `routing_test.py` (batch O-D test using `route.py`'s exact edge-weight formula).

## 4. Car / pair-9 check (2026-07-04 open item #2) — **07-04's guess refuted**

`car_check.py` flagged two full-surface pairs where car stayed on a high-risk corridor despite a
cheaper-*raw-risk* alternative. `lambda_test.py` swept λ = 0→12 on them:
- **Pair 5: car never diverges, even at λ=12.** Its route is already car-risk-optimal; the flagged
  "−41% cheaper" alternative was *another type's* optimum — lower in car raw-risk-sum but **not
  cheaper under car's actual weighted routing cost** (Dijkstra would take it if it were).
- **Pair 4: car does diverge at λ≥1.**

→ The 2026-07-04 hypothesis "*λ=1.0 is too weak*" is **not supported.** The pair-9 pattern is car
behaving **correctly** (different types have different optima), not a tuning bug. λ is not a simple
lever; raw-risk-sum is a misleading proxy for the actual weighted cost.

## 5. Two-step leakage-free validation (the confidence check before committing)

`run_cv.py` — **16-fold spatial cross-validation** (GB gridded into blocks; each held out in turn,
predicted from the rest → a fully out-of-sample national surface) **+ temporal 2024 holdout** (a
year in neither features nor target). This directly answers the "are the scores too good / is there
leakage" worry:

- **National OOS cross-type ρ = −0.097** over all 3.96M segments predicted out-of-sample.
- **Validity vs 2022–23:** car 0.083 · mc 0.183 · cycle 0.164 · lgv 0.053 · hgv 0.075.
- **Validity vs 2024 (unseen):** car 0.116 · mc 0.150 · cycle 0.167 · lgv 0.039 · hgv 0.079 —
  **≈ the target-year numbers (car even higher).** A leaking pipeline would show inflated target
  years collapsing on 2024; instead they match. **No leakage.**
- On "too good": ρ≈0 is the *noise floor* (random surfaces give ρ≈0.05 — checked), so ρ isn't the
  achievement. Validity (~0.05–0.18, positive everywhere, comparable to the statistical baseline and
  normal for sparse crash prediction) is the honest measure. Not weak — *sufficient*, and the
  contribution is explainable per-type divergence, not accuracy.

## 6. Explainability

**(a) Model SHAP** (`run_cv.py`, built-in `pred_contribs`): per-type feature importance differs
sensibly — car→area volume (`c_size`/`c_hist_all`), motorcycle→own rate + own-AADF, cycle→`c_rate_t`
(0.38), hgv→`c_share_t` (0.37).

**(b) Descriptive road-attribute association** (`road_association.py`) — over-representation
`P(attr|type)/P(attr|all)` + Cramér's V, 9 road features (chosen/rejected list in the script + the
2026-07-06 exchange). Per-type road signatures:
- **HGV** → motorway **4.81×**, 70mph 4.22×, trunk 4.01×, dual carriageway 2.30×, rural 1.87×
- **Cycle** → 20mph 1.80×, local-access 1.74×, one-way 1.72×, **roundabout 1.43×**, near ped-crossing 1.43×
- **Motorcycle** → 20mph 1.59×, one-way 1.37×, at-junction; **LGV** → motorway/70mph/trunk (milder HGV)
- **Car** ≈ 1.0 everywhere (it *is* the baseline — ~72% of crashes)
- Cramér's V: trunk 0.176, urban/rural 0.153, speed 0.119, at-junction 0.103, road_function 0.085;
  junction_control 0.012 (negligible), junction_degree 0.032 (weak).
- **Method note:** descriptive, model-free (so not undermined by geometry being a *flat predictor*).
  Caveat baked in: crash-distribution, **not** exposure-normalised risk. Label source: DfT STATS19
  2024 spec; two fields (`junction_detail`, `pedestrian_crossing`) collapsed to confident binaries
  because the 2024 numeric codes couldn't be verified — no guessed labels.

**(c) Per-route explanation** (`explain_route.py`) — for a generated route: top risk-contributing
segments + road composition + why-vs-fastest. Demo (London cycle route): **−65% cycle-risk for +0.2
min**, naming the busy A-road segments it detours around. Personalized attribute-avoidance routing
was discussed and **deferred as a future add-on** (user's call).
